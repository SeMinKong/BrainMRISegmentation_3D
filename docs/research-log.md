# 연구 보고서 · 치료 후 교종 MRI의 3D 종양 분할과 결과 검증 도구

MU-Glioma-Post(치료 후 교종 MRI) 공개 데이터로 3D U-Net 종양 분할 모델을 학습하고, 학습에 쓰지 않은 검사에서 모델이 어디서 맞고 어디서 틀리는지 웹에서 확인하는 도구까지 만든 과정을 하나의 보고서로 정리했습니다. 실험마다 **무엇을, 왜, 어떻게 했고 결과가 어땠는지**를 숫자와 함께 남기고, 재현 명령을 붙였습니다. 생성 파일은 `runs/` 아래에 있으며 Git에는 포함하지 않습니다.

## 3. 데이터 점검과 학습 목록

**한 일.** TCIA에서 받은 원본 2,978개 NIfTI(환자 203명, 검사 596회)를 전부 읽어 gzip CRC·SHA-256·shape·affine·라벨 값을 검사했습니다(`scripts/audit_mu_glioma_post.py`). 모든 파일이 240×240×155, 1 mm, LPS였고 손상은 없었습니다.

**발견.**
- 마스크 없는 검사 2개.
- 서로 다른 환자 ID 사이에 MRI 4종이 완전히 같은 쌍 11개(22개 검사). 그중 8쌍은 마스크가 다름 → 어느 쪽이 맞는지 알 수 없어 둘 다 학습에서 보류.
- 한 검사에서 T1과 FLAIR 파일이 동일 → 보류.

**결정.** 594개 중 23개를 보류하고 **571개 검사·환자 200명**을 학습 목록으로 확정(`data/mu-glioma-post-manifest.json`). 분할은 환자 단위이며 파일 내용이 같은 환자 ID들은 같은 그룹에 두었습니다(seed 42, 그룹 기준 검증 비율 0.2 → 학습 435 / 검증 136, 환자 160 / 40). 학습·검증 사이에 환자 ID나 동일 파일이 겹치는 경우는 0입니다. 검증 136개는 모든 실험에서 동일합니다.

## 4. 방법

### 4.1 전처리
T1, T1 조영, T2, FLAIR 4채널. `as_closest_canonical`로 RAS 정렬 → 1 mm 재표본화(영상 선형, 마스크 최근접) → 시퀀스별로 0이 아닌 복셀만 평균 0·표준편차 1로 정규화(배경 0은 그대로). 결과를 사례별 float16 `.npz`로 캐시합니다(`ml/cache.py`). 캐시 키는 원본 경로·크기·mtime·spacing·라벨이므로 바뀐 사례만 재생성됩니다.

### 4.2 모델과 학습
- **모델**: MONAI residual 3D U-Net, 채널 32-64-128-256-320, residual unit 2, instance norm. 출력 5클래스(배경, NETC, SNFH, ET, RC).
- **손실**: Dice + Cross-Entropy (배경 제외, softmax).
- **최적화**: AdamW, 학습률 1e-4, weight decay 1e-5, gradient clipping 12, cosine annealing으로 150 epoch에 걸쳐 1e-6까지 감소.
- **패치**: 160³, 사례당 8개. 절반은 전경 복셀 중심, 절반은 무작위. 세 축 무작위 반전. 연속 사례의 패치를 풀에 모아 배치 2로 섞음.
- **정밀도**: 학습 forward/backward만 bf16 autocast, 손실·검증·추론은 float32. cuDNN benchmark, TF32 허용.
- **검증**: 5 epoch마다 검증 136개 전체 볼륨을 sliding-window(160³, 겹침 0.5, 가우시안 가중)로 예측. `best.pt`는 검증한 epoch 중 최고만 저장.

### 4.3 증강과 라벨 균등 샘플링 (두 번째 실험)
- `--augment`: GPU에서 배치 단위로 무작위 회전(±15°), 크기(0.9~1.1), 밝기·대비·감마, 가우시안 노이즈, 가우시안 블러. 영상은 3선형, 라벨은 최근접 보간. 학습에만 적용.
- `--balanced-sampling`: 전경 중심 패치를 뽑을 때 복셀 수에 비례해 뽑는 대신, **그 사례에 있는 라벨 중 하나를 균등하게 고른 뒤** 그 라벨의 복셀을 중심으로 삼습니다. 작은 NETC가 패치 중심이 될 확률이 크게 올라갑니다.

## 5. 학습 파이프라인 최적화 (epoch당 25분 → 2.8분)

첫 실행(16채널, 배치 1, 캐시 없음)은 epoch당 25분, GPU 사용률 1~2 %였습니다. 병목은 매 epoch 435개 사례의 gzip NIfTI(2,175개 파일)를 다시 디코딩하는 것이었습니다. 병목을 하나씩 측정하고 제거했습니다.

| 단계 | 조치 | 측정 |
| --- | --- | --- |
| 1 | 전처리 결과를 사례별 float16 `.npz`로 캐시 | 571개 생성 333초(프로세스 5개), 45.9 GB. 사례 읽기 3~5초 → **0.10초** |
| 2 | 모델·배치 후보 11개를 bf16로 1 step씩 실측 | U-Net 16ch·b1 0.039 s(105 Mvox/s), 32ch·b1 0.047 s, **32ch·b2 0.080 s(102 Mvox/s)**, 16ch·b4 0.113 s, Swin UNETR f24·128³ 0.27 s(7.7 Mvox/s), f48 0.37 s |
| 3 | 패치 샘플링의 패딩·전경 인덱스 계산을 사례당 1회로, 로딩+샘플링을 스레드로 이동 | 스레드 1개 0.29 s/사례 → 4개 0.135 s/사례 |
| 4 | 배치 조립(`np.stack`, pin_memory)을 producer 스레드로 이동 | 0.132 s/step·GPU 61 % → **0.108 s/step·GPU 81 %(최대 98 %)** |
| 5 | 배치 4 시험 | 0.205 s/step = 패치당 0.051 s(배치 2와 동일), 8.0 GB. 갱신 횟수만 절반이라 **채택하지 않음** |

Swin UNETR은 같은 시간에 U-Net의 1/13 복셀만 학습하므로 기준선 단계에서는 제외했습니다. 결론: 32채널 U-Net, 배치 2, 160³, 사례당 8패치.

### 6.2 본 실행 `runs/unet3d-32ch`

라벨별(최고 epoch, 평균 / 중앙값): SNFH 0.892 / 0.941, ET 0.766 / 0.898, RC 0.595 / 0.759, **NETC 0.441 / 0.408**.

**관찰.**
- 학습 손실은 epoch 70 0.306 → 75 0.192 → 80 0.154 → 150 0.103으로 후반에 크게 떨어졌지만 검증은 epoch 85 이후 0.70 근처에서 정체 → **과적합**. 손실 급락 시점은 cosine 스케줄로 학습률이 초기의 절반이 된 때와 겹칩니다.
- NETC는 중앙값(0.41)이 평균(0.44)보다 낮아, 절반 넘는 검사에서 아예 놓치거나 크게 어긋납니다. 신호가 주변과 비슷하고 영역이 작은 것이 원인으로 보입니다.
- RC는 정답에 없는 검사가 많아(136 중 17개는 평균에서 제외) 편차가 큽니다.

### 6.3 증강 실험 `runs/unet3d-aug` (진행 중)

**가설.** 반전만 있는 증강으로는 435개 검사를 150 epoch 동안 외워 버립니다. 공간·밝기 증강과 라벨 균등 샘플링을 넣으면 검증 Dice, 특히 NETC가 오를 것입니다. 그 외 설정은 본 실행과 동일(같은 seed, split, 모델, 스케줄).

```powershell
.\.venv\Scripts\python.exe -E -m ml.train --manifest data/mu-glioma-post-manifest.json --model unet3d --channels 32 64 128 256 320 --output runs/unet3d-aug --epochs 150 --batch-size 2 --patch-size 160 160 160 --patches-per-case 8 --val-every 5 --amp --cosine --cache-dir runs/cache --prefetch 5 --loader-threads 4 --augment --balanced-sampling
```

**구현 중 트러블슈팅.** 첫 구현은 노이즈 텐서(2×4×160³ = 3,300만 원소)를 CPU 난수 생성기로 만들어 GPU로 복사했고, step 시간이 0.108 → 0.233초(GPU 48 %)로 두 배가 됐습니다. 난수 생성기를 CUDA 장치에 두자 0.127초·GPU 89 %·7.2 GB로 돌아왔습니다(증강 비용 약 +18 %). 라벨 균등 샘플링의 `argwhere`는 로더 스레드에서 처리되어 GPU 시간에는 영향이 없습니다.

**테스트.** `ml/tests/test_augment.py`: 증강 후 shape·정수 라벨 집합 유지, 같은 seed 재현, 빈 볼륨은 빈 채로 유지, 균등 샘플링이 27복셀짜리 작은 라벨을 복셀 비례 방식보다 3배 이상 자주 패치 중심으로 뽑음.

## 7. 검증 세트 전체 평가 (웹 지표, 원본 격자)

웹의 일괄 예측으로 검증 136개 전체를 `runs/unet3d-32ch`로 예측하고 판독 마스크와 비교했습니다. 학습이 GPU를 쓰는 중에 실행해 검사당 중앙값 5.3초(최대 8.7초), 전체 약 12분, 실패 0이었습니다.

| 지표 | 값 |
| --- | --- |
| 종양 전체(전경) Dice 평균 / 중앙값 | 0.904 / 0.953 |
| 라벨별 평균의 평균 (학습 로그와 같은 기준) | **0.690** (학습 로그 0.702, 격자·집계 차이) |
| NETC (판독에 있는 78개) | 0.469 |
| SNFH (136개) | 0.892 |
| ET (131개) | 0.772 |
| RC (113개) | 0.627 |
| 전경 Dice 0.9 이상 / 0.7 미만 / 0.5 미만 | 110개 / 10개 / 7개 |
| 놓친 부피 중앙값 / 더 그린 부피 중앙값 | 2.3 mL / 2.3 mL |

가장 낮은 다섯 검사는 모두 종양이 작은 검사입니다(판독 4~13 mL): `0208_T2` 0.00(4.2 mL 전부 놓침), `0066_T3` 0.08(12.6 mL 중 12.0 놓침), `0189_T5` 0.45, `0041_T1` 0.47, `0208_T1` 0.49(35 mL 중 21 놓침). 즉 실패 유형은 **작은 잔존 종양을 통째로 놓치는 것**이며, 큰 종양의 경계 오차는 작습니다. 증강 실험의 라벨 균등 샘플링이 겨냥한 바로 그 부분이므로 같은 화면으로 비교할 수 있습니다.

두 평균이 다른 이유: 웹의 큰 숫자(0.904)는 종양 전체를 한 덩어리로 본 Dice이고, 학습 로그의 0.702는 네 영역 각각의 Dice를 평균한 값입니다. 개요 화면에 두 값을 나란히 표기해 혼동을 막았습니다.

## 8. 웹 추론 파이프라인

1. **요청**: 웹이 `POST /api/jobs {case_id, model_id}` 또는 `POST /api/jobs/batch`를 보내면 서버가 단일 워커 큐에 넣고 상태(대기·실행·완료·실패)를 `GET /api/jobs/{id}`로 알립니다.
2. **입력 준비** (`ml/data.py: prepare_case`): 4시퀀스가 같은 격자인지 확인 → RAS → 체크포인트에 기록된 spacing(1 mm)으로 재표본화 → 시퀀스별 비영 복셀 z-score.
3. **체크포인트 검증** (`ml/adapters.py: validate_metadata`): `format_version`, 모델 종류, 채널 순서, 정규화 방식, spacing, 패치 크기, optimizer step 수, 라벨 의미가 MU-Glioma-Post와 같은지 확인. `torch.load(weights_only=True)`로만 읽습니다. 검증된 모델은 파일 mtime을 키로 GPU에 상주시켜 연속 작업에서 다시 읽지 않습니다.
4. **추론**: MONAI `sliding_window_inference`, 창 160³, 겹침 0.5, 가우시안 가중 합치기. 창 계산은 GPU, 합치기는 CPU(전체 logits 5×240×240×155를 GPU에 두지 않기 위해). argmax → manifest 라벨 값(0~4)으로 매핑.
5. **격자 복원** (`save_prediction`): 예측을 입력 T1의 원래 shape·affine으로 최근접 재표본화해 uint8 NIfTI로 저장.
6. **저장·지표**: 서버가 결과를 RAS로 다시 읽어 사례 격자와 일치하는지 검증한 뒤 저장하고, 판독 마스크와 비교한 지표(전체 Dice·HD95·놓친/더 그린 부피·라벨별 Dice·부피)를 분할에 저장합니다. 개요 화면은 이 저장값만 모으므로 재계산이 없습니다.

## 9. 결과 검증 도구(웹)의 설계

세 질문 순서로 화면을 짰습니다. **모델이 전체적으로 얼마나 맞는가 → 어느 검사에서 틀리는가 → 그 검사에서 어디가 틀렸는가.** 설계 원칙과 항목별 상태는 `docs/ux-plan.md`에 있습니다.

- **모델 성능 개요**: 검증 검사 전체 일괄 예측(순차 큐, 진행률), 평균·분포·영역별 평균, 먼저 볼 검사(일치도 낮은 순).
- **환자 목록 = 작업 목록**: 일치도 낮은 순·종양 큰 순 정렬, 예측 완료·절제강 필터, 검사마다 일치도 점과 숫자, 이전/다음(`←`/`→`).
- **차이 보기**: 판독∩예측 회색, 모델이 놓친 부위 파랑, 더 그린 부위 빨강을 단면과 3D에 함께 표시. 놓친/더 그린 부피(mL)를 함께 표기.
- **연결된 단면**: 단면 클릭 → 나머지 두 단면이 그 지점으로 이동 + 십자선. "종양 위치로"는 세 단면과 3D를 함께 이동.
- **발표 모드**, 진행 단계의 사람 말 표기("영상 준비 → 모델 계산 → 결과 저장"), 실패 원인 카드, 점수의 분포 속 위치(상위/하위 %), 모든 전문 용어 옆 `?` 설명.
- 성능: 단면은 uint8 볼륨을 한 번 받아 브라우저 캔버스에서 그려 휠 틱당 4 ms. 3D mesh는 직렬화·gzip 결과를 캐시해 첫 1.7초, 이후 30 ms.

## 10. 트러블슈팅

| 증상 | 원인 | 해결 |
| --- | --- | --- |
| `torch.cuda.is_available()`가 False | PyPI Windows torch는 CPU 빌드 | PyTorch 인덱스 `cu130`에서 `--force-reinstall --no-deps` 설치 |
| 검증에 epoch마다 30분 | 매 epoch 136개 전체 볼륨 sliding-window | `--val-every 5`, 검증한 epoch 중 최고만 `best.pt` |
| epoch당 25분, GPU 1~2 % | 매 epoch gzip NIfTI 재디코딩 | 전처리 결과 float16 `.npz` 캐시(`--cache-dir`) |
| 캐시 후에도 GPU 40~60 % | 메인 스레드의 패치 샘플링·배치 스택·H2D 복사 | 로더 스레드 4개 + producer 스레드 + pinned memory |
| 손실 급락 후 검증 정체 | 과적합(증강이 반전만 있음) | 증강·라벨 균등 샘플링 실험 |
| 증강 후 step 시간 2배 | 3,300만 원소 노이즈를 CPU 난수로 생성 | 난수 생성기를 CUDA 장치에 배치 |
| 웹 3D mesh 응답 7.3초 | 13 MB JSON을 매 요청 최고 압축률로 gzip | 직렬화·gzip 결과를 사례별 캐시(첫 1.7초, 이후 30 ms) |
| 단면 휠 스크롤이 느림 | 휠마다 서버에서 PNG 렌더·전송 | uint8 볼륨을 한 번 받아 브라우저에서 그림(틱당 4 ms) |
| 3D 뇌 표면이 뭉개짐 | 실효 해상도 2 mm + 닫힘 연산 2회 | 1 mm 격자, 뇌척수액(하위 22 %) 제외, σ 1.0 블러 후 marching cubes |
| 새 빌드가 화면에 안 반영 | 브라우저가 index.html을 캐시 | `Cache-Control: no-cache` 헤더 |
| 3D 탭 전환 시 시점 초기화 | 뷰어마다 카메라가 독립 | 사례별 공유 카메라 저장소(`cameraSync.ts`), 자동 회전도 공유 루프 |
| pytest가 개발자 로컬 데이터를 링크 | 기본 manifest 자동 탐색 | 테스트 픽스처에 `source_manifest=None` |
| 서버 시작 시 84개 사례가 `Permission denied: case.json.tmp`로 건너뜀 | 두 서버 프로세스가 같은 `.data/`에 같은 이름의 임시 파일을 동시에 쓰고 교체 | 임시 파일 이름에 pid·스레드 id, 내용이 같으면 쓰지 않음, Windows `replace` 실패 시 재시도 |
| 재시작마다 판독 부피 요약을 571개 다시 계산 | 링크 시 이전 `case.json`의 요약을 버림 | 링크할 때 이전 요약 유지 |
| 일괄 예측이 검사당 10초 이상 | 작업마다 50 MB 체크포인트 읽기·모델 재구성(≈1.5초) | 모델을 GPU에 상주 → 검사당 5.3초 |
| 웹의 "평균 0.90"과 학습 로그 0.70이 다름 | 웹은 종양 전체 Dice, 학습은 라벨 4개 Dice의 평균 | 개요 화면에 두 값을 나란히 표기 |

## 11. 한계와 다음 단계

- **한계.** 단일 모델·단일 seed의 결과라 신뢰구간이 없습니다. NETC(비조영 종양)는 절반 넘는 검사에서 놓치며, 작은 잔존 종양(10 mL 미만)이 주된 실패 유형입니다. 웹의 Dice는 원본 격자, 학습의 Dice는 1 mm 재표본 격자 기준으로 정의가 조금 다릅니다. 보류한 중복 사례 23개의 정답은 확정하지 못했습니다.
- **다음 단계.** ① 증강 실험이 끝나면 같은 검증 136개에서 두 모델의 분포를 비교하고 더 나은 체크포인트를 웹에 연결. ② 원본 격자 기준 사례별 평가 CSV를 만들어 학습 로그 지표와 정의를 통일. ③ nnU-Net v2 기준선 학습으로 외부 기준 대비 위치 확인. ④ 작은 종양 대응: 전경 가중 손실, 작은 라벨 중심 패치 비율 상향, 후처리(작은 성분 제거의 역효과 점검).
